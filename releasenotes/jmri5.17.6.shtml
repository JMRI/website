Release Notes for JMRI 5.17.6 release

Date: November 27, 2026

From: Bob Jacobsen

Subject: Test Release 5.17.6 of JMRI/DecoderPro is available for download.

Notes:

This is a test release. Please post a note if you encounter any new or old bugs! And please back up your JMRI files before installing this, in case you want to go back to an earlier version.

This is the next in a series of 5.17.* test releases. It requires at least Java 11 to work. We recommend that you use Java 21 if possible. (See our page on downloading Java) We expect this series to result in the next JMRI production release in December 2026. (See the tentative release schedule)

We are getting close to the next production release, so we would particularly appreciate your testing of this release to make sure it works for you. That way, if you find new problems, we can try to fix them before the production release.

JMRI is now only available under the GNU General Public License. For more information, please see our copyright and licensing page.

Update From Older JMRI Versions

If you are currently using a version older than JMRI 5.0, please follow these instructions carefully:
  1. Is your current version older than JMRI 4.12? If so, then update to JMRI 4.12 first, and ensure everything works correctly: check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Store your configuration and panel files under a new name and use those from now on. Then continue with step 2.

    If you are currently using JMRI 4.7.3 or earlier on Linux or macOS (Windows doesn't need this), then it's very important that you update to JMRI 4.12 and carrying out the migration process described in the JMRI 4.12 release note before updating to any later release.

  2. Is your current version older than JMRI 4.20? Then update to JMRI 4.20 first, and ensure that works correctly (check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Save your preferences again. Store your configuration and panel files under a new name, use those from now on, and go on to step 3.
  3. Is your current version older than JMRI 4.24? Then update to JMRI 4.24 first, and ensure that works correctly (check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Save your preferences again. Store your configuration and panel files under a new name and use those from now on.
  4. Is your current version older than JMRI 5.0? Then update to JMRI 5.0 first, and ensure that works correctly (check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Save your preferences again. Store your configuration and panel files under a new name and use those from now on.
  5. You can then install this release.
Following this multi-step order of updating via stable major releases safeguards you against possible migration issues that can arise from skipping these versions.

Older warnings

See the JMRI 5.18 release note for more warnings predating the 5.18 development series, including pointers to various migration issues. These may be relevant to you if you're updating from an earlier version; we strongly recommend you update to at least JMRI 5.0 before installing this test release. See instructions above.
  • Since JMRI 5.17.5 LogixNG formulas: && and || no longer always evaluate both sides. The right-hand side is now skipped when the left-hand side already decides the result. A formula that relies on both sides running, for example to call methods for their side effects, may now behave differently. See the LogixNG section of the release notes for an example and how to change it.
  • Since JMRI 5.17.5 If you use OpenLCB/LCC native signal masts: These can no longer be defined to use the event ID's that start with 00. The value 00.00.00.00.00.00.00.00 was previously the default for "this event ID hasn't been configured". The default is now a blank entry field that doesn't produce or consume an event. If you have defined any of the signal mast entries to start with 00, they will be migrated to be empty fields that no longer produce or consume an event.
  • Since JMRI 5.17.5 Layout Editor: an allocated block no longer automatically loses its extra color when it becomes occupied. In a Layout Block, "allocated" means the block is set to use its extra color, for example by the LogixNG Block action "Alternate Color On" or by a script, and it is what the LogixNG Block expression "Is Allocated" tests. Before, with advanced block routing on, a block set this way was switched back to its normal color without notice as soon as it became occupied. It now keeps its extra color until it is turned off, for example by the LogixNG Block action "Alternate Color Off". LogixNG and scripts that set it must now also clear it, for example when the train has left. Dispatcher and Entry/Exit are not affected: they clear their own blocks. See the Layout Editor section of the release notes.
  • Since JMRI 4.99.1 If you're using a Firefox web browser and opening JMRI help files locally (not over the web), a Firefox bug can sometimes cause it to enter a loop. There's a workaround in this JMRIusers post.

Changes since Test Release 5.17.5:

The full list of included changes is available from our GitHub code repository.

Hardware Support

CBUS

  • CBUS network connections have a new setting in Additional Connection Settings, Send frames. Some CANPi software holds back a frame that arrives while it is still handling the one before, until the next frame arrives, so events sent from JMRI are acted on late, one or more clicks behind. If that happens with a gateway that worked with JMRI 5.17.4, set Send frames to Grouped (as JMRI 5.17.4), which sends frames as 5.17.4 did.

DecoderPro

  • Fixed some problems with selecting entries when adding an entry to a roster group.
  • Improved the button language when adding an entry to a roster group.

Dispatcher

  • The Auto Allocator no longer stops allocating for a moment, with an IndexOutOfBoundsException in the log, when an allocation request is added or removed while it is looking at the list of requests.
  • Terminating an automatic train no longer freezes JMRI. Terminating waited until the train's speed read zero, and if Dispatcher gave the train another Section at that moment the train set its speed again, so the wait never ended. The same could leave that Section allocated to a train that no longer existed, so no other train could have it. A train is now stopped at once when it is terminated, and is given nothing more.
  • A Block change that an automatic train handles just after one of its Sections is released, or as the train is terminated, no longer gives warnings such as "No next Block" or that the train has disappeared. The train now uses the direction the Section was allocated in, and ignores Block changes once it is being terminated.
  • With automatic allocation, an automatic train is no longer held for good in a passing loop or before one, waiting for another train that cannot pass or meet it there. Dispatcher now plans a meet only when the other train has a free track to take, and drops the plan when the train it waits for can no longer get there: the other track is occupied or held by another train, a train has taken the other's track, or a train is already past the meeting place. Allocating by hand was needed to free the train.
  • Allocate Extra and the script call extendActiveTrainsPath now give a Section beyond the end of a train's Transit in the direction the train enters it. A train running its Transit's Sections in their reverse direction was given an extra Section forward, and extendActiveTrainsPath refused to extend its path at all. With automatic allocation on, the extra Section is now allocated by the Auto Allocator, so it no longer logs errors about the request with signal masts, or fails part way when the request is allocated while it is looking at it (JMRI/JMRI#15894).

Layout Editor

  • A large panel using Layout Block routing no longer stops with a StackOverflowError while the routing tables are built.
  • Layout Block routing tables are now complete and correct on large panels with loops, and after a connection is taken away: routes that were missed are learnt, and routes that no longer lead anywhere are withdrawn.

Roster

  • Fixed some problems with selecting entries when adding an entry to a roster group.
  • Improved the button language when adding an entry to a roster group.

Signals

  • A Signal Mast no longer keeps changing between clear and danger when automatic signal mast generation is allowed for one of its Signal Mast Logic pairs. The pair listed the mast itself among the masts that must show danger, so the mast put itself back to danger each time it cleared (seen since 5.17.5, with the turnouts set for that route).

Throttle

  • Throttle function button visibility implementation less confusing, documentation and code updated
  • Due to a Java throttle code refactoring, in Jynstruments, for ThrottleFrame jynstruments, the expected context class is now jmri.jmrit.throttle.implementation.ThrottleFrame instead of jmri.jmrit.throttle.ThrottleFrame, you can check released code in jython/Jynstruments/ThrottleFrame/Bell.jyn for instance.
