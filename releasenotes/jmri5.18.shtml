Release Notes for JMRI 5.18 release

Date: MM DD, 2026

From: Bob Jacobsen

Subject: Production Release 5.18 of JMRI/DecoderPro is available for download.

This is a draft release note only; the download links do not yet work

We are very pleased to announce that the 5.17 series of JMRI test releases has resulted in a version that's good enough to be recommended for general use, including by new users. We're therefore making that version, "Production Release 5.18" available for download today.

Notes:

JMRI is now only available under the GNU General Public License. For more information, please see our copyright and licensing page.


This release requires Java 11 to work. Java 21 is recommended.
(See our page on downloading and installing Java)


Update From Older JMRI Versions

If you are currently using a version older than JMRI 5.0, please follow these instructions carefully:
  1. Is your current version older than JMRI 4.12? If so, then update to JMRI 4.12 first, and ensure everything works correctly: check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Store your configuration and panel files under a new name and use those from now on. Then continue with step 2.

    If you are currently using JMRI 4.7.3 or earlier on Linux or macOS (Windows doesn't need this), then it's very important that you update to JMRI 4.12 and carrying out the migration process described in the JMRI 4.12 release note before updating to any later release.

  2. Is your current version older than JMRI 4.20? Then update to JMRI 4.20 first, and ensure that works correctly (check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Save your preferences again. Store your configuration and panel files under a new name, use those from now on, and go on to step 3.
  3. Is your current version older than JMRI 4.24? Then update to JMRI 4.24 first, and ensure that works correctly (check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Save your preferences again. Store your configuration and panel files under a new name and use those from now on.
  4. Is your current version older than JMRI 5.0? Then update to JMRI 5.0 first, and ensure that works correctly (check start-up, check things you need to be working, and check the JMRI log as well) before doing anything else. Save your preferences again. Store your configuration and panel files under a new name and use those from now on.
  5. You can then install this release.
Following this multi-step order of updating via stable major releases safeguards you against possible migration issues that can arise from skipping these versions.

Hardware Support

  • Fixed a race in the shared transmit code used by most connections, which could occasionally delay sending a message by about 100 ms.

CBUS

  • Console Connection Logging - Default filename now includes connection name.
  • On opening the Console, Logging to File resumes in an empty file if active when the previous console is closed.
  • Unknwon Console CAN Frames now include the hex value of the Frame.
  • Updated CBUS op-code definitions with the new VLCB op-codes so they show up nicely in the CBUS Console.
  • CBUS sensor, turnout and light addresses: an unsigned address such as 100001 is treated the same as +100001, node numbers of 21475 and above no longer overflow, and an out of range address is reported as invalid instead of throwing an exception.
  • CBUS programming reports a busy command station or a CV error straight away, instead of waiting for the programming timeout.
  • The CANCMD node variable editor shows and writes the current limits as the raw values the CANCMD firmware uses, writes the walkabout timeout from its own control, and opens for modules whose settings are outside the previous limited ranges.
  • Closing the CBUS bootloader window stops all of its timers, and the fast write speed choice is now saved.
  • The CBUS bootloader only accepts parameter replies from the module being programmed, for the parameter it asked for, and the module device ID is shown correctly.
  • CBUS performance on busy layouts: incoming frames are dispatched to sensors, turnouts and lights with much less work and no per-frame garbage, and the Event Table and Console do far less work for each frame.
  • CBUS Node Manager: teaching events now completes on modules which only accept changes in learn mode (eg. CANSERVO8C, CANMIO-SVO); an EVLRNI reply no longer throws an exception; an aborted NV fetch no longer leaves the node permanently unread; events invalidated after a failed fetch are read again; enumerating CAN IDs no longer resets an existing node; a node no longer shows JMRI's own CAN ID; and reading the events of a node with many events is faster.
  • The CBUS fast clock uses the calendar year rather than the week-based year, accepts and sends temperatures from -128 to 127 correctly, and stops listening to the JMRI clock when it is disposed. CBUS consist listeners are no longer shared between connections.
  • CBUS windows: the Node Manager releases all of its tabs when closed, NV edit windows are no longer bound to the first node they were opened for, the Console closes its log file when closed and shows when a log file could not be opened, and the SPROG 3 Plus CAN disable setting is shown instead of being greyed out.
  • CBUS Event Table: once the Event Table or the CBUS Console has been opened, adding, removing or renaming a sensor, turnout or light updates only the events it uses, instead of rebuilding the whole table each time. Loading a panel or adding beans with either window open no longer slows down as the layout grows.
  • CBUS throttles: a released throttle is removed from the session list, so an emergency stop reaches every remaining throttle instead of failing partway through; after a command station reset a recovered session is only given back to the throttle for the same loco; and nothing is sent to the layout while a throttle has no session, where previously a speed or function change could go out with an invalid session.
  • A CBUS reporter set to Classic RFID always decodes 5 byte tags as Classic RFID, whatever the first tag byte, and an existing reporter's type is never changed by the frames it receives. A reporter created by a CANRCOM RailCom report is still set to the self-describing type automatically.
  • The CBUS bootloader checks a hex file before it can be used. The Program button stays disabled until the file has been read without error and its parameters checked; a file with record types the bootloader does not understand is rejected; the MERG parameter block checksum is now verified; and a load address missing from the file stops programming cleanly instead of throwing an exception. The hex file is closed after reading instead of being left open and locked, and short records are padded correctly for the AN247 bootloader.
  • Unplugging a CANUSB4 or other GridConnect USB adapter on Windows no longer leaves JMRI running a CPU core flat out; the connection fails and reconnects when the adapter is plugged back in. Closing a connection no longer replays the last frame received.
  • GridConnect connections (CANUSB, CANUSB4, CANRS and LCC GridConnect adapters): when the ';' ending a frame is lost, the next frame is now received instead of both being merged into one corrupt frame; and corrupt frames are dropped instead of being passed on as events.
  • On a CAN Simulation connection, frames from the CBUS simulated command station, event responder and nodes now carry the time they were received, as frames from a real connection do, so raw state listeners are given when a simulated sensor event arrived.
  • CAN connections: a frame received from the layout is no longer also delivered to whichever tool sent the last frame, so a tool window which has been closed stops receiving traffic.
  • CBUS Reporters with erase-on-timeout: reading the same tag again restarts the timeout, so a tag still being read is no longer cleared early.
  • CBUS and LCC network connections using GridConnect: frames are sent at once, instead of TCP holding a frame back while an earlier one is unacknowledged (TCP_NODELAY).
  • CBUS node number requests: closing the connection, or turning off listening for node number requests, now stops a request that has just arrived from opening the node number dialogue. The "no confirmation from node" warning no longer holds up other timed tasks in JMRI while it is open.

C/MRI

  • Extend the possible reply length to support very large SUSIC installs.
  • Added a new node type, ESP32Node, for self-contained ESP32-based CMRI-over-WiFi nodes using MCP23017 I/O expander chips.
  • Network (TCP) connections now automatically attempt to reconnect if the connection is lost, instead of requiring a manual reconnect.
  • Fixed the direction the bit pattern moves in the CMRI diagnostic Output Test window, which was displaying right to left instead of left to right.

DCC-EX

  • PowerManager - Added method for requesting power status from layout.
  • Power status is polled following a set power state command as newer DCC-EX command stations do not confirm their power status following the command.
  • DCC-EX turnouts and lights now support a CS VPIN mode that drives a VPIN directly via the <z> command (DCC-EX v4.2.35+), with no pre-configuration required on the command station. Set the hardware address to the VPIN number and select "CS VPIN" as the feedback mode (turnouts) or mode (lights). The Mode column in the Light Table only appears when a DCC-EX connection is active. Requires EX-CommandStation firmware v4.2.35 or later.
  • Correct E-Stop command sent when throttle is in reverse.
  • DCC-EX: turnout commands sent with a Turnout Automation retry policy (e.g. "NoFeedback") were previously sent only once, ignoring the configured retry interval and count. DCCppTurnout now defers to the configured automation like every other connection type (issue #15471).
  • DCC-EX: messages sent by EXRAIL MESSAGE() commands are now shown in a new DCC-EX Messages window, which opens automatically when one arrives. A Messages display can also be added to Panel Editor and Layout Editor panels.

DCC4pc

  • DCC4pc RailCom readers work again: the serial port is saved in the profile, RailCom addresses and orientation are reported correctly, and two locos in one block are both identified. The reader is switched to 62.5 kbps for faster polling, recovers by itself after a loss of track power or a short, and the bus speed is restored at quit.
  • If the DCC4pc interface stops responding, unplug it and plug it back in: JMRI reconnects by itself without a restart.
  • CVs can be read and written with Programming on Main through a DCC4pc reader. Set the connection's Programmer option to the connection that sends the packets (or leave it blank to use the default command station), and choose Dcc4Pc as the Ops Mode Programmer in Preferences, Defaults. Each CV takes about half a second; any left Unknown can be picked up with Read changes on sheet.

Grapevine

  • Closing the Node Table window now stops its check of the nodes. Before, polls went on being sent for several seconds afterwards.

Lenz XPressNet

  • Fixed an issue where a throttle could stop sending speed and function commands for its locomotive after receiving an unrecognized locomotive information response, requiring a JMRI restart to recover.
  • Fixed a consist-handling bug in XNetConsist affecting rapid add/remove/delete cycles from an external JSON client, matching the equivalent LocoNet fix.
  • A throttle waiting for a reply which never arrives now gives up and resumes sending: after 5 seconds once the connection has nothing left in hand, 15 seconds otherwise. On a serial XpressNet connection a broadcast message arriving while a command is in flight could be taken for that command's reply, leaving the throttle waiting forever and silently holding back every command queued afterwards for the rest of the session.
  • Roco and Z21 throttles now stop their timers when they are disposed of, instead of leaving them running for the rest of the session.

  • Added interpretation of some BDL716 configuration messages to LocoNet Monitor.
  • Made some LocoNet-specific programming mode constants public so the can be accessed from scripts.
  • LocoNet Clock now uses the same throttle ID as the rest of JMRI, instead of (illegal) 00 00.
  • Fixed several consist-handling bugs that could leave a LocoNet consist in an inconsistent state after rapid add/remove/delete operations from an external JSON client (e.g. a WiFi throttle panel), including cases that could report a consist change as failed when it had actually succeeded.
  • Added a new JSON service, loconetSlotUsage, that reports live LocoNet slot usage (used/free/total) over both the HTTP and WebSocket JSON APIs, so external clients can detect slot exhaustion before a consist or throttle operation fails.

Absent that, they wouldn't appear. A description is no longer required; if one is not present, the Sensor or Turnout will be created without a user name.

OpenLCB / LCC

  • The Event Table now automatically persists its content so it can be used while disconnected from your main LCC network. For example, you could load the Event Table at your club, then open that same profile at home and see all the same contents.
  • Support for the configuration display "checkbox" hint has been added.

The value 00.00.00.00.00.00.00.00 was previously the default for "this event ID hasn't been configured". The default is now a blank entry field that doesn't produce or consume an event. If you have defined any of the signal mast entries to start with 00, they will be migrated to be empty fields that no longer produce or consume an event.
  • Change the default events for the STL Editor IQYZ tables from all zeros to unique zero based events.
  • When configuring a node, the Segment and Group levels are now color coded (blue for invalid value; orange for changed value) the way the group tabs and individual values have been.

Dispatcher

  • Fixed a bug where auto trains could not be run after the Dispatcher window had been closed and reopened in the same JMRI session.
  • An automatic "Head and Tail" train with no stopping sensor and no speed profile stopping can now draw fully into a Section before stopping, by watching the Block holding its tail go unoccupied, as an "Entire Train" train does. Previously it stopped as soon as the locomotive entered the Section.
  • When the maximum speed of an automatically running train is entered as a scale speed (scale mph or scale km/h), that limit is now applied as entered. Previously it could be reduced by the stored throttle percentage value in the Physics ramp and in distance-based stopping. The throttle percentage is now only a fallback for locomotives without a speed profile, or when the profile does not cover the direction of travel; a warning is written to the system console in that case.
  • Dispatcher: the Release button in the Allocated Sections table now releases only a train's oldest Section once the train has left it, or its furthest allocated Section before the train reaches it, so that a train's route is never left with a gap. The Section directly ahead of a train can only be released while the train is stopped, and you are then asked whether to terminate the train. With Auto Allocate on, the train's allocation is held after such a release. After the furthest allocated Section is released, the train is allocated that Section again when it carries on, instead of silently getting no further allocations.
  • The scale speed conversions for the maximum speed and the scale speed shown for the minimum throttle now follow the "Run in reverse" setting, and the scale km/h entry is no longer labelled as scale mph.
  • Fix TSA Go to Manual and Resume from Manual.
  • Automatic release of Sections no longer releases a Section when the next Section has not been entered, or when the train is stopped, waiting or in manual mode.
  • Trains using "Head Only" or "Head and Tail" train detection must now have a Max Train Length, whether or not they run automatically. A train without one is refused when it is added or loaded, with a message saying why. The Max Train Length field is now shown for these trains even when they do not run automatically.
  • Sections behind a "Head Only" train are now released using the train length for every train, not only automatic ones. Previously a dispatched or manual "Head Only" train had each Section released as soon as the locomotive left it.
  • For a "Head and Tail" train a Section is now released using the train length, measured to the head, as for a "Head Only" train. Previously, if the tail lost detection, for example through dirty wheels, Sections could be released while the train was still in them, all the way up to the head.
  • An automatic train's speed ramp no longer carries on after the train is halted, and a new ramp no longer runs alongside an old one when the speed is changed quickly.
  • Trains waiting for a fast clock departure or restart time now start when the clock passes that time, even if the clock jumps over the exact minute. Before, they waited a whole fast clock day. If the clock is set back, only the exact minute counts.
  • An automatic train now always finds the correct next Block in its Section. Before, block or signal changes at the same moment could give it the wrong Block or none. Reversing or resetting a train that fills its Section no longer fails.
  • Restarting a train no longer starts allocating before the release of its old Sections has finished, and no longer freezes the screen while it waits. A second Restart of a train that is already being reset is ignored.
  • Automatic release of Sections is faster when many Sections are allocated, as each check now goes through the allocated Sections once. Which Sections are released is unchanged.
  • An automatic train no longer sometimes takes its next Block to belong to another train when one of its Sections is released at the same moment. Before, a warning was written that the new current signal mast is null, and the train's speed was set from its allocations instead.
  • Automatic allocation now plans meets in passing loops for opposing trains on single track, including trains running their Transit in reverse; before, meet planning never took effect. A plan is dropped when one of its trains is terminated, finishes or is reset, so the other train is not held. Working out another train's position no longer halts that train, and a dispatched train no longer stops allocation for other trains.
  • Automatic allocation does less work on each scan, and a scan or automatic release check is no longer queued again while the same check is already waiting, which reduces delays with many automatic trains on large panels.
  • When a train is terminated while an automatic release is waiting, a Section it held is no longer released twice. Before, an error was logged and the Section could be set free while it was allocated to another train.
  • With "Use roster entry" and "Place train name in allocated Blocks", the roster entry now goes into the Blocks ahead of a train in a Section used in reverse, not the Blocks behind it. The alternate color for allocated Blocks is put ahead of the train in the same way.
  • With "Place train name in allocated Blocks", a Block that is in two allocated Sections keeps showing the train name until both are released.
  • A train that is reset at the end of its Transit and restarts after a delay now starts to stop when its head enters the last Section, even when its tail is still in the Section before.
  • A Section released just as its train starts back, to reverse or to run its Transit again, is no longer left allocated to nobody but not free. Before, it could never be allocated again, and a train needing it waited for ever at a signal.
  • When an automatic train's stop is cancelled, for example because the signal clears or an allocation arrives, its end, reversal or reset action is now dropped too. Before, it could run later, wherever the train next stopped.
  • An automatic train's Block changes are now handled one at a time, in the order they happen. Before, each change was handled separately, so a train entering two Blocks in quick succession could be stopped for entering a Block out of turn, a short Block crossed at speed could be missed, and a train could be stopped with "No next Block". Every change is now acted on, including a detector that bounces, so use the sensor debounce settings for such detectors.

A route is no longer marked invalid while another active path in the block still uses it, and removed routes and through paths stop listening to their block and turnouts.
  • With advanced block routing on, a block now sends a routing update to its neighbours only when its status (occupied, reserved, empty or unknown) changes, not on every change to the block such as a new reporter value. This reduces the work done on large layouts.
  • Finding the Layout Block for a Block no longer searches every Layout Block each time. This speeds up advanced block routing, Signal Mast Logic, Dispatcher and Entry/Exit on large layouts.
  • With advanced block routing on, the shortest route to a destination is now found when it is the first or only route, so changes to block lengths are passed on through the layout.
  • With advanced block routing on, when two routes to a destination are equally good, the same one is now always chosen: the one with fewer blocks, then by the name of the next block. Before, the choice could change after an unrelated edit to the layout.
  • Layout Editor block routing: the path search now finds routes that exist when the preferred branch has two or more dead-end or occupied sub-branches. Before, NX, Dispatcher ad-hoc routes and Signal Mast Logic could report "no route" in these cases.
  • Layout Editor block routing: route costs and hop counts now reach every block when a block's metric changes, and the routing tables are correct straight after loading, so routes no longer prefer a siding. Updates are no longer dropped after long running, so Dispatcher, Entry/Exit and Signal Mast Logic choose routes from correct costs.
  • Layout Editor block routing no longer overflows the stack when a block changes while a routing update is on its way round a loop of blocks.
  • An allocated block, that is one set to use its extra color, for example by the LogixNG Block action "Alternate Color On" or by a script, now keeps its extra color until it is turned off, for example by the LogixNG Block action "Alternate Color Off". The LogixNG Block expression "Is Allocated" tests this. Before, with advanced block routing on, the block was switched back to its normal color without notice as soon as it became occupied. LogixNG and scripts that set it must now also clear it, for example when the train has left. Dispatcher and Entry/Exit are not affected: they clear their own blocks.

    • NX - Entry/Exit Tool

    • NX with signal masts: if a train enters the start block while the route is still being set, the first block of the route stays protected. Before, it was dropped and the entry signal could stay clear behind the train.
    • NX: when a train reaches a block of a route without being seen in the block before it, that block now keeps the value it already has, for example from RFID, and is only given the train's value if it has none. A block that is not part of the route is no longer changed. Block values further along a route might therefore differ from earlier versions.

Logix

  • Logix: a deleted Logix now stops running. Before, deleting an enabled Logix left it setting turnouts and sensors until JMRI was restarted. This includes a Logix that was loaded disabled and enabled later, which could not be stopped this way even where the delete did deactivate it.
  • Logix: Logixes whose actions trigger each other in an endless loop are now stopped, and an error names the Conditionals in the loop. Before, the loop ran until Java's stack overflowed, and other listeners on the sensor or turnout that started it were skipped. A loop through so many Logixes that the stack still overflows first now logs where it started.
  • Logix: a Conditional that tests the same item (for example a sensor, turnout, memory or signal head) in more than one state variable is now calculated once per change instead of once per state variable, so with "Execute Actions whenever triggered" its actions run once per change and a toggle action no longer cancels itself.
  • Logix: Conditionals with a mixed antecedent are calculated many times faster, with the same results.
  • Logix: finding the Logix that a Conditional belongs to is faster, which helps large Logix setups that use cancel-timer actions or Conditional lookups by system name.
  • Logix: a delayed set sensor or set turnout action now always acts on its own sensor or turnout, even if the Conditional's actions were reordered or edited while the delay was running, and no longer keeps repeating after such an edit. This lets a check guard what follows it, for example (x != null) && (x.y == 1). A formula that relied on both sides always being evaluated, to call methods for their side effects, must be changed. For example, myArray.add("Hello") || myArray.add(" ") || myArray.add("World!") now only adds "Hello": add returns true, so || has its answer after the first call and skips the rest. Use myArray.add("Hello") && myArray.add(" ") && myArray.add("World!") instead, which carries on while each call returns true.

  • LogixNG: local variables are now cleared away after Return, Exit, Break, Continue or an error. Before, a ConditionalNG used more memory every time it ran.
  • LogixNG: events are no longer lost, and LogixNG no longer stops running, when it falls behind, for example while an error dialog is open, or after an unexpected error. A warning is logged if it falls a long way behind.
  • The LogixNG Logix action, which Logixes imported into LogixNG use, now treats its first result as a change whether it is true or false, as a Logix conditional does. Before, a first result of false counted as no change, so actions set to run on a change to false did not run until the result had first been true.

Signal Masts

  • A Signal Mast Logic mast now goes to danger as soon as a block on its route becomes occupied, instead of first waiting for the signal logic delay; changes back towards clear are still delayed as before.
  • Generating Signal Mast Logic Sections no longer stops at the first Source:Destination pair whose Section name is already used by a user-defined Section: only that pair is skipped. A user-defined Section also keeps its forward mast.
  • Signal Mast Logic now only sends an aspect to its source mast when the aspect changes. Before, every re-check of the logic, for example when a block or turnout changed on any route from the mast, sent the same aspect again, giving extra traffic on the layout and a brief flicker on masts set to reset previous states. A mast whose hardware has lost its aspect, for example after a power cycle, now keeps its old output until the aspect next changes.
  • A Signal Mast Logic mast keeps following its logic if setting its held aspect fails. Before, it stopped changing until JMRI was restarted. If the held aspect is disabled for the mast, the danger aspect is used instead.
  • Signal Mast Logic no longer misses a change, such as a mast being released or a route sensor, turnout or block changing, that happens just as it is working out a mast's aspect. Before, the mast could keep the old aspect until something else changed, and in rare cases could show a proceed aspect with part of the route against it.
  • With Dispatcher's "Use alternate color for allocated Blocks", Signal Mast Logic now gives danger for a block shown in the alternate color only when it is held by a train other than the one approaching the mast, or by no Dispatcher train. Before, it guessed from the direction of its own Section, so a mast whose Section was not part of the train's Transit held that train at danger, and the blocks listed in the logic by the user were never checked. Each Section now records the train holding it.
  • When Signal Mast Logic starts, it now uses the same route checks as when a block, turnout or mast changes. Before, a user-set mast overriding an automatic one was tested the wrong way round, blocks set to "any state" always failed and Dispatcher reservations were ignored until the first change. Starting the logic again no longer adds its listeners twice.
  • Turning off "Use Layout Editor Paths" for one destination of a source mast no longer stops Signal Mast Logic Sections being generated for that mast's other destinations.
